# B minor compiler

This is a (non-optimising) compiler for the "toy" language "B minor", a language designed for introductory compiler creation while still being powerful enough to write serious programs. 
This compiler began as a project on learning how to write a parser, and turned into writing a functional (but non-optimising) compiler. Of course, essentially being a hobby project, this was entirely human written.
It currently compiles to GAS assembly targeting x86-64.

I am placing this here for posterity; I spent a lovely March 2026 learning how to write a compiler and building this.
 I followed the notes in ["Introduction to Compilers and Language Design"](https://dthain.github.io/books/compiler/), which gives an outline of the design of a compiler.
Some parts of their notes are (much) more of an outline than others, particularly around the DAG and code generation part. 
Optimisation is not discussed. 

Being on my own and rather inexperienced, I made some rather terrible design decisions, especially around the DAG/CFG stage of the project.
I thought (and still think) control flow optimisation was really cool, so after converting my AST to a DAG I further converted it to a CFG. 
The CFG was poorly designed and ended up making code generation a nightmare (or rather, I couldn't think of a good way to handle cycles). 

The code is presented more-or-less as it was written in March/April. I have removed the more embarassing comments (I didn't check variable names), and reorganised the folder structure so it looks more modular.

This may serve as a sort of reference (or inspiration) for fellow learners of compiler writing. 
Otherwise, I wouldn't recommend using this for anything. I plan on writing a second one with all the lessons I learned from this project. I also plan on editing some notes I wrote during the project and putting them in the `notes` folder.

Some points:
- One actual contribution here is a working nontrivial Pratt parser in C. The Pratt parser is an excellent design which is both more powerful and much simpler than a deterministic PDA (i.e. an LR(1) parser), allowing hand-written parsers which are likely faster than ones built with Bison.
 Unfortunately, all of tutorials I found at the time were using an OOP or functional language (even Pratt uses LISP in his original paper). 
I've moved it near the top of `parser/parser.c` (at `parse_expression`, `expr_nud`, `expr_led`); it demonstrates that not only is writing a Pratt parser in C feasible, it is incredibly easy.
- Note: in the Pratt parser I used a massive if/else branch, which could be written "more simply" with a jump table. You could even write some Python script to automate the process, a sort of much simpler Bison. 
If you so wish, you could make it dynamic too like the OOP people do, but I don't think it's worth the complexity.
- Simpler Pratt parsers for reference are in the `pratt` folder.
- The lexer was generated by `flex`. I wrote my own DFA engine, but I didn't end up turning it into a lexer, mostly because I didn't end up learning how to do that. I find FSAs much cooler than hand-written lexers, so I would happily do it again.
- Let the `dag_and_cfg` code (and the resulting `code_gen` code) demonstrate a lesson to think about the design before you start writing.  That said, I didn't know what I was doing.
I also included Ershov numbers because I liked the mathematical aesthetic of it, but I found it difficult to handle function calls with it. I would love to fix the design when I have time.
- There are a lot of long sections in the code, but they are mostly repetitive if/else statements. I think otherwise it's relatively simple.
